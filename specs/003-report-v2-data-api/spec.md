# Feature Specification: 报告展示数据接口（Report View API）

**Feature Branch**: `003-report-v2-data-api`  
**Created**: 2026-09-18  
**Status**: Draft  
**Input**: User description: "报告的前端在 @report/report-v2 这个文件夹下，我要撰写这个报告对应的数据接口，用于支持报告的展示，接口由 nepstarAdmin 的后端 api 给出"

## 背景

`reportFront/report-v2` 是当前唯一维护的长寿指数报告前端，目前所有展示内容来自一份写死的模拟数据。nepstarAdmin 后端已有健康管理配置数据（指标、方案、商品）和管理端报告查询接口，但没有任何面向报告查看页面的展示接口：现有报告详情接口只返回报告基础信息，明细固定为空。

本特性定义一组由 nepstarAdmin 后端提供的报告展示数据接口，使 V2 报告首页与系统二级详情页能够用真实报告数据完整呈现。已有一份接口设计建议位于 `docs/V2-首页报告后端接口.md`，本特性将其正式立项。

### 现状核查结论（2026-09-18）

对后端所连的两个数据源（旧系统 MySQL `platform` 库、报告 MongoDB）做只读核查后确认：

**报告本体在 MongoDB，不在 MySQL。**

- 报告文档位于 MongoDB 的 `receive_report` 库，collection 为 `reportV2Info`（另有 `reportInfo` 为旧版结构、`algorithmicRequestBean` 为设备上传的原始算法请求、`tb_receive_report` 为空）。`_id` 即报告编号，形如 `KH503LS0005865V220721182530852`。
- 文档顶层结构固定：`sex`（0=女 / 1=男）、`robotSn`、`reportDate`、`userInfo`（含身高体重）、`ddsReportInfo`、`ecgReportInfo`、`spo2hReportInfo`、`skinReportInfo`。
- `ddsReportInfo.firstTarget[]` 就是报告的一级系统树，每项含 `targetId` / `score` / `inspectAge` / `secondTarget[]`；二级再含 `threeTarget[]`（带 `score` 与 `lastScore`）。
- **报告文档里没有名称、没有权重、没有字符串编码，只有数字 `targetId`。**
- 核查了 4 份真实报告（2 男 2 女，含 KH503 与 KJ501 两种机型）：一级系统恒为 10 个、顺序恒定。

**指标字典与权重在 MySQL `platform.inspect_target`。**

- `target_id` / `inspect_name` / `parent_id` / `inspect_level` / `proportion`（权重）/ `sort` / `sex`。
- 一级 10 个系统的权重依次为 30/20/15/8/5/5/5/5/5/2，二级也有各自的 `proportion`。
- 因此"旧库代码 ↔ 后台指标编码"的映射就是 **数字 `targetId` ↔ `sa_indicator`**，不存在原先设想的另一套不透明编码体系。

**性别专项是数据天然分好的。**

- 生殖系统（`targetId` 3143）下的二级指标按报告 `sex` 返回不同分支：女性报告返回女性功能 / 子宫附件 / 乳腺，男性报告返回男性功能 / 前列腺。V2 的"女性功能""男性功能"两个系统即来源于此，后端不需要自行推断性别归属。

**V2 的展示结构是对旧数据的重组，不是改名。**

- V2 的八个系统中，消化系统 / 内分泌 / 骨骼 / 免疫力 与旧一级 1:1 对应；"心血管""肺功能"取的是旧一级"循环系统""呼吸系统"下的**二级**名称；"女性功能""男性功能"是生殖系统下的二级分支；旧一级中的营养状态 / 有害物质 / 皮肤系统在 V2 里不展示。
- 这意味着映射关系是一次**产品口径的重新分组**，已由用户确认（见本节末尾的展示口径确认）。

**展示口径已确认（2026-09-18）**：V2 的系统与指标清单**照设计稿逐项映射到真实数据**，映射方式是在指标管理里逐个登记 `targetId`，未登记的不展示。

- 系统级：8 个系统的得分来源已定——消化/内分泌/骨骼/免疫力/心血管/肺功能取报告文档中的一级得分；女性功能与男性功能取生殖系统下对应二级分支的得分。旧一级中的营养状态 / 有害物质 / 皮肤系统不进入 V2 展示（10 − 3 + 1 = 8）。
- 指标级：真实数据是三层结构（一级系统 → 二级 → 三级）。V2 设计稿列出的指标对应的是**三级**指标，跳过中间的二级层。经逐项核对，设计稿列出的指标在真实数据中**全部存在**，无需补齐数据，也没有口径冲突。例如骨骼系统下的骨质疏松 / 骨质增生 / 颈椎钙化 / 腰椎钙化，与真实数据 `3128` 下的三级指标逐字相同；免疫力系统的 6 项与 `3136` 下的 6 项完全相同；女性功能系统下的 5 项分别是 `3154` 黄体酮 / `3224` 内分泌失调指数 / `3159` 宫颈炎指数 / `3160` 阴道炎指数 / `3162` 乳腺增生风险。

因此**不存在原先设想的"设计稿列了 5 个而数据只有 3 个"的偏差**——那是把三级指标误读成二级所致。

## Clarifications

### Session 2026-09-18

- Q: 报告展示接口怎么拿旧库的报告数据？ → A: 实时只读查询旧库——每次请求按报告编号定位报告主记录，再按报告版本读对应明细表，不做同步或缓存。
- Q: 旧库代码 → 后台指标编码的映射配置由谁、用什么方式维护？ → A: 使用现在后台的指标管理模块，由登录后台的人员维护——不新建独立映射管理页面，映射信息随指标记录一起维护。
- Q: 报告图表的数据与元数据，前后端职责怎么分？ → A: 后端出类别与系列——类别与系列由指标记录与得分派生；图表类型与单位由报告前端按系统标识固定维护。
- Q: 跨报告的历史趋势图（心血管"近 6 次"折线）纳入本期吗？ → A: 本期支持——接口按客户向前取最近若干次同系统得分组成趋势序列，只纳入与本次同一报告版本口径的历史。
- Q: 报告"尚未就绪"这个状态怎么判定？ → A: 看旧库报告主记录的状态与报告生成时间——不以明细结果是否已生成作为判定依据，避免把本来就没有明细的报告误判为未就绪。
- Q: 报告"不存在"与"无权访问"对外是否区分？ → A: 对外统一——两者返回同一错误标识，仅内部日志区分，避免通过错误差异枚举有效报告编号。
- Q: 详情接口返回的指标权重，以哪边为准？ → A: 以旧库为准——权重取自旧库指标字典，映射登记不重复维护权重，保证加权能解释旧库的系统得分。
- Q: 旧库超时或不可达时，报告展示接口怎么行为？ → A: 超时 → 报告暂不可用——对旧库访问设超时，超时或不可达时返回独立的"报告暂不可用"错误，前端提示可重试，不返回残缺报告。
- Q: 报告展示接口的响应时间目标定多少？ → A: P95 ≤ 3 秒——首页与详情接口各自，给旧库宽表查询与趋势历史查询留余量。
- Q: 报告展示接口的日志与访问审计做到什么程度？ → A: 结构化日志即可——记录报告编号、结果状态、耗时与缺失映射的旧库代码；不新增访问审计表与留存策略。
- Q: 系统详情里的"直接采集"值从哪来、怎么归到系统？ → A: 取旧库报告级单值字段——用报告主记录上的微循环/血氧饱和度/心电状态等单值，按固定的系统归属规则挂载，不走指标映射登记；字段稀疏时按缺失隐藏区块处理。
- Q: 系统的状态、摘要、结论解读、行动建议这些文案从哪来？ → A: 指标管理模块维护文案——在指标记录上维护并随报告输出，不接入旧库文案目录，也不由后端套模板生成。
- Q: 趋势序列取最近多少次历史报告？ → A: 固定 6 次——与 V2 现有图表设计一致，不做后台可配置。
- Q: AI 咨询入口与页面功能开关存在哪里、由谁维护？ → A: 本期固定值——接口按约定值返回入口启用与保存报告关闭，不引入后台配置项或管理界面；US5 据此改写。
- Q: 模拟数据回退的边界怎么定？ → A: 本期即移除回退——报告前端不再保留模拟业务数据，接口失败统一展示对应错误状态。

*以下四条来自 2026-09-18 的数据源只读核查（非 /speckit-clarify 提问），用于修正上文因数据源误判而产生的条目：*

- 修正：报告本体在 MongoDB `receive_report.reportV2Info`，不在 MySQL。上文"实时只读查询旧库并按报告版本读明细表"中的"明细表"应理解为该 collection 的文档；`A3087` 一类代码列不再是报告明细的载体。
- 修正：指标标识是数字 `targetId`，与 MySQL `inspect_target.target_id` 及后台 `sa_indicator` 直接对应；原设想的"不透明旧库代码 → 指标编码"映射层与 `sa_indicator_legacy_code` 表不再需要。
- 修正：直接采集值在 `reportV2Info.spo2hReportInfo`（血氧、微循环）与 `ecgReportInfo`（心率、心电状态），不在 `inspect_base`。
- 修正：性别专项系统由数据天然分好（生殖系统 `targetId` 3143 按报告性别返回不同二级分支），后端不需要自行推断性别归属。
- 修正：上文多处出现的"报告版本"概念不再适用——报告文档统一在 `reportV2Info` 一个 collection 内，趋势序列的口径一致性约束改为"同源且结构口径一致"（FR-035），而非按版本表区分。
- 修正：后端目前没有任何 MongoDB 连接；新增该只读连接属于架构变更，已获用户确认，`.env` 已配置 `MONGODB_URL`。

*以下两条为 2026-09-18 的口径确认（用户决定）：*

- 确认：V2 的系统与指标**照设计稿逐项映射到真实数据**，通过指标管理逐个登记 `targetId` 实现；未登记的不展示。系统得分取报告文档中对应层级的得分（6 个系统取一级，女性/男性功能取生殖系统下的二级分支）。
- 确认：原记录的"女性功能 5 个指标 vs 真实数据 3 个二级指标"**不是数据缺口**——V2 设计稿列的是三级指标，真实数据三层结构中全部存在。该项作废。

*以下为 2026-09-18 的后续澄清（针对 /speckit-analyze 发现的缺口）：*

- Q: 健康预期寿命在旧系统里根本不存在，这个字段怎么处理？ → A: 按公式派生——采用"基准年寿 + 年龄差修正"形式（FR-045），不由后台配置、也不隐藏该卡片。
- Q: 派生公式的具体形式？ → A: 基准年寿减去（生理年龄 − 实际年龄）。基准值取设计稿 mock 反推的 86.8（84.6 = 86.8 − (44.2 − 42)），需业务最终确认。
- Q: 指标的"是否参与加权"怎么定？ → A: 树内全加权，删掉该字段——报告指标树内的指标全部参与加权，不参与加权的只有树外的直接采集值，因此接口不返回加权标记。
- Q: 哪些系统需要返回趋势序列？ → A: 仅心血管——与 V2 的"近 6 次"折线图一致，其余系统的趋势序列为空，且适用系统不做后台可配置。
- Q: 趋势序列的"口径一致"怎么判定？ → A: 同一报告文档集合（同一 collection）即视为同源——两种机型的一级系统与 `targetId` 相同、得分口径一致；按机型过滤会让多数客户凑不满 6 次，结构漂移改由字段存在性容错兜住。
- Q: `focus_system_codes`（重点系统）留还是删？ → A: 删除——前端从未引用（只在 mock 数据里定义过一次），保留它需要新增 FR 与实现却无消费方，按宪法 Principle II 移除。

*以下两条来自 2026-09-18 的字段来源核查（针对 /speckit-analyze 的 U1 与新增歧义）：*

- Q: 同龄人对比比例从哪来？ → A: 取旧库报告主记录的排名字段——核查确认该字段即百分位（旧系统文案"你的得分好于全国 X% 的人"，取值 0–100 且与总分单调对应），五份 V2 报告全部有值，按报告编号关联即可，不需要新增数据。
- Q: 实际年龄取哪个字段（客户档案年龄与受检年龄差 2–3 岁，且前者存在 0 值）？ → A: 取报告文档的**受检年龄**——五份样本全部有效，且与生理年龄在同一对象内配对；客户档案年龄在样本中有 0 值，会导致页面显示"实际年龄 0 岁"。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 打开报告首页看到自己的真实报告 (Priority: P1)

作为报告查看者，我打开自己的报告链接后，希望看到本次检测的总分、是否处于警示区间、报告编号与日期、我的实际年龄与生理年龄、健康预期寿命、超过同龄人的比例、本次总体结论，以及每个身体系统的得分卡片。这些内容必须来自我这一次的真实检测结果，而不是一份固定的演示数据。

**Why this priority**: 首页是报告的入口，也是用户判断"这份报告是不是我的"的唯一依据。没有真实数据，整个页面只有演示价值。

**Independent Test**: 用一份真实报告请求首页数据，逐项核对报告编号、日期、年龄类指标、总分与系统得分，再换一份不同性别的报告验证性别专项系统随报告变化。

**Acceptance Scenarios**:

1. **Given** 一份已生成的报告，**When** 报告前端请求该报告的首页数据，**Then** 返回该报告的报告编号、检测日期、性别、总分与警示阈值，且这些值来自这份报告的真实记录。
2. **Given** 报告总分低于警示阈值，**When** 首页数据返回，**Then** 原始总分与阈值同时返回，页面据此进入警示状态；总分不低于阈值时返回的数值同样能让页面进入正常状态。
3. **Given** 报告包含多个已评分的身体系统，**When** 首页数据返回，**Then** 每个系统都带有稳定的系统标识、名称、得分、状态描述、一句摘要、后台计算的展示顺序，以及该系统卡片所需的图表数据与指标摘要。
4. **Given** 一份女性报告，**When** 首页数据返回，**Then** 只返回适用于女性的身体系统，男性专项系统不出现；男性报告则相反。
5. **Given** 后台配置了系统的展示优先级，且存在低分且命中推荐方案的系统，**When** 首页数据返回，**Then** 这些系统的展示顺序由接口直接给出，报告前端按接口给定顺序渲染，不自行推断业务顺序。
6. **Given** 报告编号不存在、报告尚未生成完成，或请求者与报告不匹配，**When** 请求首页数据，**Then** 接口返回可区分的明确错误，报告前端可以据此展示对应的错误状态而不是空白页。

### User Story 2 - 进入系统详情看到与首页完全一致的数据 (Priority: P1)

作为报告查看者，我在首页点击某个身体系统后进入二级详情页，希望看到该系统在首页上同样的得分，以及构成这个得分的二级指标、图表、直接采集值、结论解读和行动建议。

**Why this priority**: 首页与详情页分数不一致会直接摧毁用户对报告的信任，这是 V2 现有流程的核心一致性要求。

**Independent Test**: 对同一份报告，逐个系统比对首页返回的得分、状态、摘要、图表数据与详情接口返回的对应字段，要求完全一致；再验证每个详情都返回了该系统自己的指标、结论与行动建议。

**Acceptance Scenarios**:

1. **Given** 用户从首页进入某一系统的详情，**When** 请求该系统详情数据，**Then** 返回的系统名称、得分、状态与摘要与首页返回的同一系统完全一致。
2. **Given** 某个系统的得分由若干二级指标加权构成，**When** 请求该系统详情数据，**Then** 返回该系统下每个二级指标的名称、得分与权重，且指标得分按权重能解释该系统得分。
3. **Given** 某个系统存在不参与加权评分的直接采集结果，**When** 请求该系统详情数据，**Then** 这些采集结果被单独返回并明确标注为不参与评分。
4. **Given** 某个系统带有结论解读和行动建议，**When** 请求该系统详情数据，**Then** 两者都被返回供详情页展示。
5. **Given** 请求的系统标识不属于该报告，**When** 请求系统详情数据，**Then** 接口返回明确的"系统不属于该报告"错误，而不是回退到第一个系统。
6. **Given** 同一份报告，**When** 分别请求首页和某系统详情，**Then** 两次请求返回的该系统得分、图表序列与推荐内容同源，不出现第二次计算带来的偏差。

### User Story 3 - 低分系统展示匹配的健康管理方案与商品 (Priority: P2)

作为报告查看者，当我的某个系统得分偏低、且后台为该系统的具体问题配置了健康管理方案时，我希望在首页卡片和该系统详情页中看到匹配的方案说明，以及方案关联的商品图片和名称。

**Why this priority**: 推荐方案是报告从"看结果"走向"做管理"的关键，但它建立在真实得分之上，必须先有 P1 的数据通路。

**Independent Test**: 用一份内分泌与骨骼得分偏低的报告，验证这两个系统在首页和详情都返回了各自匹配的方案与商品，且其他系统不返回任何推荐。

**Acceptance Scenarios**:

1. **Given** 内分泌系统下的松果体相关指标得分偏低且后台配置了对应方案，**When** 请求首页或内分泌详情数据，**Then** 返回该方案的问题描述、方案名称、管理说明、标签，以及方案关联的商品名称与图片地址。
2. **Given** 骨骼系统下的骨量相关指标得分偏低且后台配置了对应方案，**When** 请求首页或骨骼详情数据，**Then** 返回骨骼方案及其关联商品。
3. **Given** 某个系统得分正常或后台未为该系统的指标配置方案，**When** 请求该系统数据，**Then** 推荐字段为空，报告前端不展示占位推荐卡片。
4. **Given** 同一指标被后台关联了多个方案，**When** 组装推荐，**Then** 按后台配置的优先级与顺序选出唯一推荐，同一方案下的多个商品按配置顺序全部返回。
5. **Given** 某个指标、方案或商品被后台停用，**When** 组装推荐，**Then** 已停用的对象不出现在报告数据中。
6. **Given** 用户在首页看到了某个推荐，**When** 用户进入对应系统详情，**Then** 详情页返回同一方案与同一商品集合，不出现首页与详情不一致。

### User Story 4 - 在指标管理中维护 targetId 与报告文案 (Priority: P2)

作为后台指标维护人员，我希望在现有的"健康管理 → 指标管理"里，为每个一级、二级指标登记它在报告数据中对应的数字标识，同时维护报告上要展示的状态、摘要、解读与建议文案，这样报告展示接口才能把真实得分落到正确的指标上、并用后台确认过的文字呈现，而不需要研发每改一次内容就发一次版本。

**Why this priority**: 它是首页与详情看到真实数据的先决条件；但它服务的是后台人员而非报告查看者，且可以独立于报告页面单独验收，因此排在 P1 之后。

**Independent Test**: 在指标管理页给某二级指标登记 `targetId` 并保存，重新打开报告展示接口，验证该指标得分出现在报告里；改回或清空后再验证结果随配置变化，全程不改代码。

**Acceptance Scenarios**:

1. **Given** 指标维护人员处于指标管理，**When** 为某个二级指标登记其 `targetId`，**Then** 保存成功且在指标详情中可回看该对应关系。
2. **Given** 某个指标已登记 `targetId`，**When** 报告展示接口组装该系统数据，**Then** 该指标的得分按登记关系取自报告文档。
3. **Given** 指标维护人员改动了某指标的 `targetId`，**When** 重新请求同一份报告，**Then** 输出随配置变化，不需要发布新版本。
4. **Given** 同一 `targetId` 被登记到两个指标，**When** 保存或组装报告数据，**Then** 冲突被明确提示，不出现同一份得分落到两个指标上的静默结果。
5. **Given** 某个指标未登记任何 `targetId`，**When** 组装报告数据，**Then** 该指标不出现在报告系统中，其余指标与整份报告仍正常返回。
7. **Given** 指标维护人员为某个一级指标填写了摘要、结论解读与行动建议，**When** 重新请求包含该系统的报告，**Then** 报告用新文案呈现该系统，不需要发布新版本。
8. **Given** 某个一级指标尚未维护报告文案，**When** 组装报告数据，**Then** 该系统仍返回得分与指标，文案字段为空，页面隐藏对应文字区块，不得用旧库文案或模板文字顶替。

### User Story 5 - 报告页面从接口获取入口配置与功能开关 (Priority: P3)

作为报告查看者，我希望报告页面上的 AI 长寿咨询入口和保存报告开关由接口统一给出，这样报告前端不必把这些值内置在代码里；将来引入配置能力时，前端不需要跟着改。

**Why this priority**: 属于接口完整性，不阻塞核心报告阅读；本阶段取值固定，因此优先级最低。

**Independent Test**: 请求首页数据，核对返回的 AI 咨询入口配置与保存报告开关与本期约定值一致，并确认后台不存在任何修改它们的入口。

**Acceptance Scenarios**:

1. **Given** 本期约定 AI 咨询入口启用，**When** 请求首页数据，**Then** 返回入口标题、入口类型与目标地址。
2. **Given** 本期约定保存报告能力关闭，**When** 请求首页数据，**Then** 返回明确的关闭状态，报告前端不展示保存入口。
3. **Given** 本阶段不提供配置能力，**When** 检查后台管理端，**Then** 不存在修改这两项的页面、接口或配置项。

---

### Edge Cases

- 报告编号不存在时，必须返回明确的"报告不存在"错误，不能返回空对象让页面渲染成空白报告。
- 请求中的客户标识与报告归属的客户不一致时，必须拒绝访问且不返回报告内容；对外必须返回与"报告不存在"完全相同的错误标识，内部日志记录真实原因。
- 报告主记录存在但状态无效、或报告生成时间尚未落定时，必须返回"报告尚未就绪"类错误，与"报告不存在"可区分。
- 报告主记录已就绪但完全没有明细结果时，不得报"尚未就绪"；应按可得数据降级返回报告基础信息与总分。
- 报告记录了某个系统但该系统本次没有得分（未采集或不适用）时，系统仍应返回，得分为空值，且不参与首页排序中的低分判断。
- 系统不适用于报告所属用户的性别时，不出现在返回结果中。
- 图表类别与图表数值数量不一致、或数值缺失时，接口必须保证返回的图表数据自洽，页面不得出现错位或缺项的图表。
- 报告文档中的某个 `targetId` 未登记到任何指标时，该系统或指标按可得数据降级展示，不得因为缺少登记而让整份报告请求失败。
- 报告文档存在结构漂移（已在真实数据中观察到同一 collection 内文档字段数不一致，如皮肤信息一段存在 37 与 33 两种字段数）时，接口必须按字段存在性容错读取，不得因缺失字段抛错或返回残缺报告。
- 报告文档的一级系统多于 V2 展示的八个时（真实数据恒为 10 个），未进入 V2 展示口径的系统必须被排除，且不得因此影响其余系统的得分与排序。
- 推荐方案的商品图片地址不可访问时，推荐数据本身仍应返回，页面负责展示替代文本与回退状态。
- 行动建议或结论解读缺失时，对应字段为空数组或空值，页面隐藏对应区块，不得展示占位文案。
- 报告文档中的报告级单值采集字段缺失或为空时（该组字段并非每份报告都有），该系统的直接采集区必须为空，页面隐藏该区块，不得补零或用"未知"等占位值。
- 直接采集值与二级指标得分落在同一个系统下时，两者必须分区呈现，不得让不参与加权的采集值混入加权得分列表。
- 同一份报告被重复请求时，返回结果必须稳定，不得因图表序列或推荐匹配的随机性出现前后不一致。
- 客户是首次检测、没有任何历史报告时，趋势序列为空，页面降级为无趋势展示，报告其余内容必须正常返回。
- 历史报告中某一次缺少该系统得分（未采集或不适用）时，该次直接跳过，不得补零，也不得让序列长度失真。
- 历史报告的结构口径与本次不一致时，该次历史不纳入趋势序列。
- 报告性别标识缺失或取值不在已知范围内时，必须按无法判定处理：不猜测性别分支，返回明确的错误状态或降级为不展示性别专项系统，不得随意套用另一性别的内容。
- 历史报告数量多于 6 次时，只取最近的那 6 次，且必须是最新的 6 次。
- 旧库超时或不可达时，必须返回"报告暂不可用"而不是残缺报告，也不得把基础设施故障显示成"报告不存在"或"报告尚未就绪"。
- 旧库返回超时后，重复请求同一份报告必须能正常恢复，不得因上一次失败而持续返回不可用。
- 接口返回任一失败状态时，报告前端必须展示与该失败原因对应的错误状态；不得回退到演示数据，也不得展示空白报告或部分内容。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供报告首页展示数据接口，一次返回该报告首页所需的全部数据，报告前端不需要再拼装多个后台配置接口。
- **FR-002**: 首页数据 MUST 包含报告标识、报告展示编号、检测日期、用户性别、总分、警示阈值、同龄人对比比例、实际年龄、生理年龄、健康预期寿命与总体结论。
- **FR-003**: 首页数据 MUST 返回该报告下每一个适用身体系统的系统标识、名称、得分、状态描述、摘要与展示顺序。状态描述与摘要 MUST 取自指标管理模块维护的系统文案，MUST NOT 由本特性另行硬编码。
- **FR-004**: 首页数据 MUST 为每个系统返回图表数据，包含由该系统二级指标派生的类别与一一对应的得分序列，并能同时支撑二级详情页的图表展示；图表类型与单位 MUST 由报告前端按系统标识固定维护，接口 MUST NOT 返回。
- **FR-005**: 首页数据 MUST 为每个系统返回二级指标摘要，至少包含指标名称与得分。
- **FR-006**: 首页数据 MUST 为每个系统返回紧邻该系统的推荐方案内容（如命中），使推荐可以显示在对应问题下方。
- **FR-007**: 系统 MUST 提供系统二级详情数据接口，按报告与系统标识返回该系统自身的完整详情。
- **FR-008**: 系统详情数据 MUST 包含构成系统得分的二级指标列表，每条包含指标名称、得分与权重；权重 MUST 取自旧库该指标的字典配置，MUST NOT 使用后台另行维护的权重。
- **FR-009**: 系统详情数据 MUST 包含该系统不参与加权评分的直接采集结果，并明确标注这些值不参与评分。这些值 MUST 取自报告文档中的报告级单值（血氧饱和度、微循环、心率、心电状态），按固定的系统归属规则挂载，MUST NOT 走指标映射。
- **FR-010**: 系统详情数据 MUST 包含该系统的结论解读与行动建议，两者 MUST 取自指标管理模块维护的系统文案。
- **FR-011**: 系统详情返回的系统得分、状态、摘要、图表数据 MUST 与首页返回的同一系统完全一致。
- **FR-012**: 系统 MUST 依据报告性别过滤性别专项身体系统：男性报告不得返回女性专项系统，女性报告不得返回男性专项系统。性别归属以报告数据中生殖系统下的二级分支为准（女性报告返回女性功能/子宫附件/乳腺，男性报告返回男性功能/前列腺），后端 MUST NOT 自行推断或二次分配。
- **FR-013**: 系统 MUST 由后端计算并返回身体系统的最终展示顺序，报告前端仅按该顺序渲染，不自行推断业务顺序。
- **FR-014**: 展示顺序 MUST 使低分且命中推荐方案的系统优先于其他系统。
- **FR-015**: 系统 MUST 按"报告指标结果 → 指标配置 → 方案关联 → 方案 → 方案商品关联 → 商品"的关联链组装推荐，推荐必须匹配到具体指标而不是名称模糊匹配。
- **FR-016**: 系统 MUST 只返回启用状态的指标、方案与商品。
- **FR-017**: 系统 MUST 在同一指标命中多个方案时按后台配置的优先级与顺序选出唯一推荐；同一方案关联多个商品时按配置顺序全部返回。
- **FR-018**: 首页与系统详情 MUST 由同一套组装逻辑产出推荐，保证同一系统在两处的推荐方案与商品一致。
- **FR-019**: 系统 MUST 在内部区分"报告不存在""无权访问""报告尚未就绪""系统不属于该报告""报告暂不可用"五种失败情形；对外 MUST 把"报告不存在"与"无权访问"合并为同一错误标识返回，MUST NOT 通过错误差异暴露报告是否存在，内部 MUST 记录可区分真实原因的访问日志。"尚未就绪" MUST 依据旧库报告主记录的状态与报告生成时间判定，MUST NOT 以明细结果是否已生成作为判定依据。
- **FR-020**: 系统 MUST 返回首页所需的 AI 咨询入口配置（启用状态、标题、入口类型、目标地址）与报告页面功能开关（如保存报告是否可用）。本阶段这些值 MUST 为固定值，MUST NOT 引入后台可配置项、配置页面或配置接口。
- **FR-021**: 系统 MUST NOT 要求报告查看者持有管理后台的登录凭证；报告展示接口的访问控制与后台管理接口的访问控制相互独立。
- **FR-022**: 系统 MUST 在组装数据时保证输出自洽：图表类别与数值一一对应，系统得分可由返回的指标得分与权重解释，不出现互相矛盾的字段。
- **FR-023**: 报告查看者 MUST NOT 能通过接口获取不属于自己的报告内容。
- **FR-024**: 报告结果数据 MUST 取自报告文档（MongoDB `receive_report.reportV2Info`）中该报告的真实记录，包括报告级得分与 `firstTarget` 层级树；系统 MUST NOT 在本特性中自行计算报告得分。
- **FR-025**: 报告中的系统与指标 MUST 通过数字 `targetId` 与后台 `sa_indicator` 关联；该关联关系 MUST 通过后台现有的"指标管理"模块维护，由已登录的后台用户完成，MUST NOT 为此新建独立的管理页面。
- **FR-026**: 指标记录 MUST 能够登记其对应的 `targetId`，一级指标与二级指标均可登记；维护人员改动登记内容后，报告输出随之变化，不需要修改代码或发布新版本。
- **FR-027**: 后台 MUST 能区分哪些旧一级系统进入 V2 展示、哪些不展示：消化/内分泌/骨骼/免疫力与旧一级一一对应；心血管与肺功能取自旧"循环系统""呼吸系统"（得分取该一级的得分，展示的指标取其下的三级）；女性功能与男性功能取自生殖系统的性别分支（得分取该二级分支的得分）；营养状态 / 有害物质 / 皮肤系统不进入 V2 展示。
- **FR-028**: 当报告文档中的某个 `targetId` 找不到对应的启用指标时，系统 MUST 跳过该项并保留其余数据，不得使整份报告请求失败；未命中的 `targetId` MUST 可被排查。
- **FR-029**: 系统 MUST 以报告编号 + 客户标识作为报告展示接口的访问参数，并校验报告确实归属于该客户；不匹配时拒绝访问。
- **FR-030**: 本特性 MUST 同时交付 `reportFront/report-v2` 的前端接入：新增数据请求与字段适配，使页面组件使用的展示结构保持不变。
- **FR-031**: 报告数据 MUST 在每次请求时从报告文档实时只读获取，本特性 MUST NOT 把报告结果同步或缓存到本地库；接口对报告数据源与旧库均保持只读，不写入、不修改任何旧系统数据。
- **FR-032**: 同一 `targetId` MUST NOT 被登记到多个指标；后台保存时必须拒绝或明确提示该冲突，组装报告时 MUST NOT 把同一份得分落到两个指标上。
- **FR-033**: 报告展示接口 MUST 能通过指标管理模块的增删改查接口读写指标的 `targetId` 登记内容，且该读写 MUST 沿用后台现有的登录与权限控制。
- **FR-034**: 系统 MUST 为**心血管**返回该客户最近 6 次同系统得分的趋势序列，序列按时间升序排列，并与本次得分同源同口径；其余系统的趋势序列 MUST 为空。适用系统与次数 MUST NOT 做成后台可配置项。
- **FR-035**: 趋势序列 MUST 只纳入与本次报告属于同一报告文档集合的历史；读取历史文档时 MUST 按字段存在性容错，不得假定历史文档结构与本次完全一致；可得历史少于 6 次时 MUST 按实际可得次数返回而不是补零或截断成固定长度。
- **FR-036**: 缺少历史报告时，系统 MUST 仍返回本次报告的全部数据，趋势序列为空，页面降级为无趋势展示，不得使整份报告请求失败。
- **FR-037**: 指标权重 MUST 取自旧库指标字典（`inspect_target.proportion`）。进入报告展示的每项指标 MUST 在字典中有对应记录，其权重即为该记录的 `proportion`；报告文档自身不提供权重，后端 MUST NOT 在后台另行维护一套权重。报告指标树内的指标**全部参与加权**，不参与加权的只有树外的直接采集值（FR-009），因此接口 MUST NOT 返回"是否参与加权"标记。
- **FR-038**: 系统 MUST 对每次报告数据源与旧库访问设置超时；任一数据源超时或不可达时 MUST 返回独立的"报告暂不可用"错误标识，与"报告尚未就绪"可区分，MUST NOT 返回缺少系统明细的残缺报告。
- **FR-039**: 系统 MUST 为每次报告展示请求输出结构化日志，至少包含报告编号、结果状态与耗时；发生未命中指标时 MUST 记录未命中的 `targetId`。日志 MUST NOT 记录报告内容、客户姓名或联系方式。
- **FR-040**: 系统 MUST NOT 在本特性中引入报告访问审计表或访问留存；访问追溯能力不在本期范围内。
- **FR-041**: 指标管理模块 MUST 支持为一级指标维护状态描述、摘要、结论解读与行动建议，并支持为二级指标维护说明文案；这些文案 MUST 可增删改，改动后报告输出随之变化，不需要发布新版本。
- **FR-042**: 系统 MUST NOT 从旧库文案目录读取报告解读与建议文案，也 MUST NOT 由后端按得分区间套模板生成；报告文案的唯一来源是指标管理模块。
- **FR-043**: 报告前端 MUST NOT 保留模拟业务数据回退；`src/data/report.js` 中的业务值 MUST 被移除或改为仅承载接口数据的容器，接口失败时 MUST 展示与失败原因对应的错误状态，MUST NOT 用演示数据顶替真实报告。
- **FR-044**: 每个系统下展示的指标 MUST 由后台逐个登记 `targetId` 决定，未登记的指标不出现在报告中；登记范围对应 V2 设计稿列出的指标，其在真实数据中位于旧一级系统下的第三层。系统得分 MUST 取报告文档中对应层级的得分，MUST NOT 由所展示的指标重新加权计算。
- **FR-045**: 健康预期寿命 MUST 由基准年寿减去（生理年龄 − 实际年龄）派生，基准值取 86.8，结果保留一位小数。该值 MUST NOT 读自报告数据源（源里不存在该字段），MUST NOT 由后台按年龄段配置；基准值 MUST 以后台配置项的形式给出，便于业务调整。
- **FR-046**: 报告摘要各字段的来源 MUST 如下：总分、生理年龄取自报告文档；**实际年龄取自报告文档的受检年龄，MUST NOT 取客户档案年龄**（档案年龄存在无效的 0 值）；同龄人对比比例取自旧库报告主记录的排名字段并按整数返回；健康预期寿命按 FR-045 派生。同一份报告在报告文档与旧库主记录上重复出现的字段（总分、受检年龄、性别）MUST 以报告文档为准。

### Scope Boundaries *(mandatory)*

- **Canonical Target**: `nepstarAdmin/backend`（报告展示数据接口的提供方）；`reportFront/report-v2`（前端接入方）。
- **Explicitly In Scope**: 报告首页展示数据接口、系统二级详情数据接口、报告文档（MongoDB）与旧库字典（MySQL）的实时只读读取、`targetId` 到后台指标编码的关联、指标管理模块中登记 `targetId` 与维护报告展示文案的能力（含其增删改查接口与冲突校验）、报告级直接采集单值到系统的固定归属、性别专项系统过滤、系统展示排序、报告得分与阈值的原样返回、趋势序列的组装、推荐方案与商品的匹配组装、AI 咨询入口配置与页面功能开关、访问参数与归属校验、`reportFront/report-v2` 的数据请求与适配接入，以及随接入移除其中的模拟业务数据。
- **Explicitly Out of Scope**: 报告得分与生理年龄等业务结果的计算逻辑；报告长图/PDF 生成与下载接口；AI 咨询真实会话接口；面向第三方的独立历史趋势查询接口（趋势序列只随报告数据返回）；历史数据的回填、补算与跨口径归一；报告访问审计表、访问留存与报告分享控制；限流与配额；报告内容的多语言输出；AI 咨询入口与页面功能开关的后台可配置化（本阶段固定值返回）；报告数据源与旧库任何形式的写入或结构变更；报告结果的同步、缓存或离线导入；新建独立的管理模块或菜单；`reportFront/baogaoV2`、任意 V3 目录、`reportFront/长寿指数UI设计`、`KH503`；`oldbackend`（旧报告后端，只作为取值口径的参考，不修改）；后台管理端既有报告、方案、商品接口的改造，以及指标管理模块中与 `targetId` 登记、报告展示文案维护无关的既有行为调整；报告页面的视觉设计、文案与布局调整；部门过滤配置的调整。
- **Architecture Decision**: 保留现有管理端接口不变，新增一组面向报告展示的聚合接口，由后端完成权限校验、系统映射、排序、指标匹配与推荐组装；同时新增一个到报告文档 MongoDB 的只读连接。**新增 MongoDB 作为数据源是架构变更，已获用户确认**（`.env` 已配置 `MONGODB_URL`）。在指标记录上新增 `targetId` 登记并据此扩展指标管理模块的既有接口与页面，同属已确认的架构变更。若后续需要写入报告数据源、在旧库中新增表或视图、或引入新的对外访问凭证机制，仍须先取得用户确认。已有一份接口设计建议 `docs/V2-首页报告后端接口.md` 可作为起点，其接口路径、响应字段与错误编码需在契约文档中确认后再实施。

### Key Entities *(include if feature involves data)*

- **报告**：一次长寿指数检测的结果载体，在旧系统中已有真实记录，包含报告标识、展示编号、检测日期、所属客户、性别、总分与总体结论。报告是首页与详情两个接口的共同根对象。
- **报告摘要**：报告上的年龄与对比类信息，包含实际年龄、生理年龄、健康预期寿命、超过同龄人比例与警示阈值。
- **身体系统**：报告中的一级模块（如内分泌、骨骼、心血管），包含系统标识、名称、得分、状态、摘要、展示顺序与适用性别范围。系统的得分由其次级指标结果构成。
- **系统二级指标结果**：构成系统得分的具体指标项，包含指标标识、名称、得分与权重；部分指标带有原始采集值与单位，并标注是否参与加权评分。
- **报告文档**：报告数据源的单元，一份报告一个文档，以报告编号为键。包含报告级得分、一级系统的层级树、报告级单值采集结果，以及所用设备的标识。它是报告展示接口的唯一内容来源。
- **报告指标树**：报告文档内按层级组织的结果结构，一级为身体系统、二级为系统下的指标、三级为细分项；每一项携带数字 `targetId` 与其得分。它是"系统得分"与"二级指标"两类展示内容的共同来源。
- **指标 `targetId`**：报告文档中表示一项系统或指标的数字标识，与旧库指标字典及后台指标记录直接对应。它是连接报告数据与后台配置的唯一纽带，取代了原先设想的字符串编码体系。
- **指标上的 `targetId` 登记**：指标记录上新增的对应关系信息，把报告文档中的数字标识与后台指标编码连起来。它由指标管理模块维护，是本特性使报告真实数据能够落到正确指标上的关键实体。
- **指标展示文案**：指标记录上维护的面向报告的文案，一级指标承载状态描述、摘要、结论解读与行动建议，二级指标承载自身说明。它是报告文字内容的唯一来源。
- **图表数据**：随系统返回的可视化数据，包含由该系统二级指标派生的类别与一一对应的数值序列，以及趋势图所需的按时间排列的历史序列。图表类型、标题与单位属于报告前端的固定视觉映射，不作为接口实体的一部分。
- **健康管理方案**：与某个低分指标匹配的管理方案，包含方案标识、名称、说明与标签，并关联一个或多个商品。
- **商品**：方案下向用户展示的物品，包含商品标识、名称与图片地址。
- **报告展示配置**：影响报告页面呈现的非业务配置，包含 AI 咨询入口配置与保存报告等功能开关。本阶段它是一组由接口返回的固定值，不是可维护的数据实体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 报告首页的每一项展示内容（报告基础信息、年龄类信息、总分与警示状态、各系统卡片、图表、指标摘要、推荐内容）都能从接口返回的数据中获得，报告中不再存在只能由前端硬编码提供的内容。
- **SC-002**: 对同一份报告，首页与全部系统详情返回的系统得分、状态、摘要、图表序列与推荐内容一致率达到 100%。
- **SC-003**: 系统中每个系统的得分都能由该接口同时返回的二级指标得分与权重完整解释，无未解释偏差。
- **SC-004**: 女性报告不出现任何男性专项系统，男性报告不出现任何女性专项系统，性别过滤正确率为 100%。
- **SC-005**: 低分且命中推荐方案的系统在展示顺序中排在其他系统之前，在全部验收报告中顺序正确率为 100%。
- **SC-006**: 通过报告编号与客户标识请求其他客户的报告时，100% 被拒绝且不泄露报告内容。
- **SC-007**: 对外错误标识可区分四种情形——报告未就绪、系统不属于该报告、报告暂不可用、报告不可用；"报告不存在"与"无权访问"对外返回完全相同的标识，内部日志可区分两者，判定正确率 100%。
- **SC-008**: 用户在报告首页与系统详情之间往返时，不需要额外请求后台管理端接口，单次页面数据由一次请求完成。
- **SC-009**: 在一份已登记 `targetId` 的验收报告上，接口返回的系统与二级指标数量、名称与得分，与报告文档按登记关系解析出的结果逐项一致，一致率 100%。
- **SC-010**: 在指标管理模块修改某指标的 `targetId` 登记后重新请求同一份报告，接口输出随配置变化，全过程不需要改动代码或发布新版本。
- **SC-011**: 趋势序列长度不超过 6，取值与旧库中该客户同版本历史报告的同系统得分逐项一致，一致率 100%；可得历史少于 6 次时序列长度等于实际可得次数，不出现补零。
- **SC-012**: 在指标管理模块登记一个已被占用的 `targetId` 时，保存被拒绝或明确提示，重复登记成功率为 0。
- **SC-013**: 首页接口与系统详情接口的 P95 响应时间均 ≤ 3 秒。测量基准为 20 份不同报告的串行请求，每份报告各请求一次，不含并发压力。
- **SC-014**: 报告数据源或旧库超时、不可达时，100% 返回"报告暂不可用"，不出现残缺报告、也不误报为"报告不存在"或"报告尚未就绪"；数据源恢复后同一报告的后续请求 100% 正常返回。
- **SC-015**: 任意一次未命中指标或失败请求，都能仅凭结构化日志定位到具体报告编号与未命中的 `targetId`，定位成功率 100%，且日志中不出现报告内容或客户联系方式。
- **SC-016**: 报告中出现的状态描述、摘要、结论解读与行动建议 100% 来自指标管理模块维护的文案；在指标管理模块改动文案后重新请求同一份报告，输出随之变化，不需要发布新版本。
- **SC-017**: 首页接口返回的 AI 咨询入口配置与保存报告开关与本期约定值一致，且后台不存在任何可修改它们的页面、接口或配置项。
- **SC-018**: 报告前端不再包含任何模拟业务数据；接口返回失败时，100% 展示与失败原因对应的错误状态，验收中不出现演示报告、空白页或残缺内容。
- **SC-019**: 每份报告返回的系统数恒为 7：V2 定义的 8 个系统中，女性功能与男性功能按报告性别二选一，其余 6 个恒定出现；营养状态 / 有害物质 / 皮肤系统在任何报告中都不出现。
- **SC-020**: 每个系统的得分与报告文档中对应层级的得分逐项一致（6 个系统对 `firstTarget[]` 的得分，女性功能 / 男性功能对生殖系统下对应二级分支的得分），一致率 100%，且不由所展示的指标重新加权得出。

## Assumptions

- 报告展示接口面向已持有报告链接的报告查看者，与管理后台的登录用户是不同的人群，两者访问控制相互独立。
- 旧库对后端保持只读，本特性不写入、不修改旧库任何表。
- 身体系统与指标在后台已有稳定的编码体系；报告文档中的数字 `targetId` 与这些编码的对应关系是登记内容。**展示口径已确认**：V2 的系统与指标照设计稿逐项映射，旧一级中的营养状态 / 有害物质 / 皮肤系统不展示；报告文档中的三层结构（一级系统 → 二级 → 三级）中，V2 展示的指标位于第三层，中间层不单独展示；系统得分取报告文档中对应层级的得分（FR-027、FR-044）。
- 展示哪些指标由后台在指标管理里逐个登记 `targetId` 决定。登记内容对应 V2 设计稿列出的指标清单；该清单已在真实数据中逐项核对存在，实施时按设计稿逐个登记即可。
- 报告文档的集合内已观察到结构漂移（同一 collection 中文档字段数不一致）。本特性按字段存在性容错读取，不假定文档 schema 完全统一；跨口径的统一不在本特性范围内。
- 本环境配置的部门在旧库报告表中没有任何报告，属预期情况，本特性不做处理；报告文档侧的端到端验收需要另行指定一份可用的参考报告或测试数据。
- 报告文档的读取依赖 MongoDB 连接。该连接的可用性与凭据由 `.env` 的 `MONGODB_URL` 提供；本特性不实现连接的重试、连接池调优或故障转移策略，只按 FR-038 在不可用时返回"报告暂不可用"。
- 报告编号（`report_code`）同时用作 MongoDB 文档主键与 MySQL 报告主记录的关联键，两处必须一致；若出现只在其中一侧存在的编号，按"报告不存在"处理。
- **健康预期寿命的基准值 86.8 是从 V2 设计稿 mock 反推的**（mock 为 实际 42 / 生理 44.2 → 84.6）。旧系统两处数据源都没有该字段，也无任何计算该值的代码。基准值以配置项形式实现，业务确认后可直接调整，不需要改代码。
- 报告摘要字段的来源已全部核实（2026-09-18）：同龄人对比比例取自旧库报告主记录的排名字段（该字段即百分位，旧系统文案为"你的得分好于全国 X% 的人"）；实际年龄取报告文档的受检年龄而非客户档案年龄；生理年龄取报告文档中的对应值；健康预期寿命按 FR-045 派生。五份真实报告验证：报告文档与旧库主记录在总分、受检年龄、性别三项上逐条一致。
- 报告页面的视觉状态映射（分数颜色、光晕、卡片色调、图标、布局、图表类型与单位）继续由报告前端按系统标识固定维护，接口只提供原始得分、阈值与图表类别/系列。
- 报告前端不再保留模拟业务数据回退。`reportFront/report-v2` 现有测试中依赖固定模拟值（总分 68、内分泌 58、骨骼 54 等）的断言必须随接口接入改为基于测试数据或接口返回值的断言，否则会与新行为冲突。
- 旧库访问超时值的设定必须在 SC-013 的 3 秒预算之内，使超时请求落在可接受的响应时间分布里，而不是让超时本身成为尾延迟的主因。
- 报告访问审计、访问留存与分享控制不在本期范围内，源文档本身也将其列为后续阶段；本期只保证能通过结构化日志排查问题。
- 报告文案改由后台指标管理模块维护后，可能与用户在旧报告页面看到的历史文案不一致。这是为换取文案可控与不再新增映射链而确认接受的取舍。
- 用于报告文案的指标记录一旦被停用，按 FR-016 该指标不进入报告；文案随着指标一起消失，不单独保留。
- 报告前端的页面级性能预算以本特性的接口目标为准：既有 V2 迁移验收中"页面 2 秒内可见"是在无接口调用的模拟数据前提下达成的，接入真实接口后该数值不再作为报告页面的验收指标。
- 已有接口设计建议 `docs/V2-首页报告后端接口.md` 是本特性的主要输入，其中与现有后端响应规范不一致的部分（如统一响应码取值）以后端既有规范为准。
