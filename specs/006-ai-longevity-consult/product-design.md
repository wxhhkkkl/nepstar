## 1. 产品定位

将现有“AI 长寿咨询”入口升级为一位**能结合当前报告解释问题、查证数据、适度追问并提出行动建议的 AI 健康管理助手**。

它要帮助用户完成三件事：看懂报告、理解值得关注的变化、知道下一步可以做什么。页面名称沿用“AI 长寿咨询”，对话中的角色称“AI 长寿顾问”，清楚标识 AI 身份。

“长寿”是健康管理主题，不是根据检测分数预测死亡年龄或保证延长寿命。报告上的指标分数与派生估计，均按其真实来源和解释范围使用。

## 3. 首版用户旅程

1. 用户在报告首页点击悬浮入口，或在已有管理方案中点击“咨询 AI 长寿顾问”。
2. 进入空白咨询欢迎页，保留健康管理方案；服务可用时直接显示输入框，不增加强制同意步骤，也不代访问者写入同意记录。正式告知与授权方案在上线前完成独立确认。
3. 进入聊天欢迎页，顶部标明当前报告日期。无需重新填写已经有且获准使用的信息。
4. 用户点击快捷问题或输入自己的问题，看到“正在读取报告依据”等真实进度，随后逐步看到答案。
5. AI 使用相关指标和本次咨询上下文；确有必要时补问一至两个问题，再给行动建议。
6. 用户可展开依据回看指标、继续追问、停止生成或重试。返回聊天与返回报告都恢复原阅读位置。

普通问题的当前路径是“进入 → 点击一个问题 → 读到答案”。无选择记录不阻断本地获准试用；已有明确撤回须阻断生成，不通过重新进入页面忽略同一凭证的选择。

## 4. 移动端页面设计

沿用当前浅蓝/灰白背景、深蓝正文、轻描边和圆角样式。页面占满移动端可用宽度，正文不小于 16 px，左右保持适度内边距，不依靠点击放大阅读。

### 4.1 欢迎页

| 位置 | 内容 | 交互规则 |
| --- | --- | --- |
| 顶部栏 | 返回、AI 长寿顾问 | 返回来源页；不展示会话记录入口 |
| 报告条 | “正在结合：本次报告”＋真实检测日期 | 点击展开少量报告摘要，不重复放置巨大的总分卡 |
| 欢迎信息 | “你好，我可以结合这份报告，帮你理解指标、查看变化，并梳理下一步可以做的事。” | 标明 AI 身份，不显示未生成的健康结论 |
| 快捷问题 | “帮我看懂这份报告”“哪些指标值得关注”“我可以从哪里开始改善” | 有相关数据时可将其中一项替换成真实指标问题；点击即发送 |
| 输入区 | “输入你想了解的健康问题…”、发送按钮 | 默认文字输入，不放没有功能的语音/拍照按钮 |
| 底部提示 | “AI 回答仅作健康管理参考” | 轻量常驻；完整说明放在首次使用和说明入口 |

欢迎页不堆放多组推荐卡、历史咨询和商品。每次进入都展示空白咨询，阅读层次只有“我在问哪份报告”“可以问什么”“在哪里输入”。

### 4.2 对话页

- 用户消息靠右，使用淡蓝气泡；AI 消息靠左，采用宽松白色内容区，减少重复头像与厚重边框。
- AI 首次普通回答建议 150–300 字，先直接回答问题，再展示必要依据与建议；用户要求时再展开细节。
- 有依据时，答案下方提供“依据：本次报告 · 相关指标”，点击展开名称、分数与真实日期，可继续进入指标页。
- 操作区只保留复制、“有帮助/没有帮助”以及必要的重试；生成中以“停止”替换发送。
- 完整答案后由模型结构化返回最多两个与当前主题有关的追问建议，追问与答案正文分开显示。只在最新回答下展示；已在同报告同指标会话中展示或已询问过的问题不重复提供。追问记录绑定已核验指标引用保存，刷新可恢复，仅用于服务端去重，不发送给模型。
- 输入框固定在底部，避让软键盘和安全区；最多扩展到四行，之后在输入区内部滚动。
- 用户在底部时跟随本次新内容；向上读本次对话时不自动拖回底部，显示“有新回复”。
- AI 页面内不再叠加首页悬浮咨询按钮。

### 4.3 方案入口的差异

从管理方案进入时，在报告条下方增加一条轻量提示：“正在咨询：实际方案名称”。输入区预填“为什么给我推荐这个方案？”，由用户发送。

回答先解释关联的实际指标和推荐条件，再介绍方案资料。商品信息不先于报告解释；用户问“我的指标什么意思”时，不自动插入购买引导。原页面的方案已下架或失效时，咨询需说明这一点。

### 4.4 必须完成的页面状态

| 状态 | 用户看到什么 | 可以做什么 |
| --- | --- | --- |
| 进入加载 | 报告条、欢迎区的骨架屏 | 等待或返回 |
| 新咨询 | 简洁空态和本次可问问题 | 开始本次咨询 |
| 报告未就绪/不可用 | 对应说明与返回入口 | 重试或回报告 |
| 会话凭证失效 | 当前标签页的聊天凭证无效或过期 | 保留公开报告访问；从该报告开始新的匿名咨询 |
| 等待/生成 | 读取依据或生成回答的实际状态 | 停止；无需暴露内部推理过程 |
| 停止/中断 | 已显示的部分与“回答未完成” | 重新生成，原问题保留 |
| 网络失败 | 原问题旁的失败提示 | 重试，不重复创建问题 |
| 额度不足/维护 | 清楚的恢复时间或稍后重试说明 | 阅读已有内容、返回报告 |
| 超时 | 可恢复的超时提示 | 停止和重试，不无限显示加载动画 |

## 5. 核心能力与优先级

| 能力 | 用户会怎么问 | 首版行为 |
| --- | --- | --- |
| 整份报告解读 | “帮我看懂这份报告” | 简要说明报告内容，按真实数据提示可进一步了解的项目 |
| 单项指标解释 | “肺功能这个分数意味着什么？” | 查对应指标定义、分数和维护文案，说明分数的解释范围 |
| 历史比较 | “这次比上次有变化吗？” | 查同指标有效历史，给真实日期与变化，不把差值直接等同疾病好转/恶化 |
| 必要追问 | “我最近总觉得累，报告能说明吗？” | 区分自述与检测信息，围绕问题补问，无法从报告确认时明确说明 |
| 行动建议 | “那我接下来能做什么？” | 给最多三个有条件、可开始的行动，说明何时回顾或寻求专业帮助 |
| 方案解释 | “为什么推荐这个方案？” | 使用当前报告已匹配方案及已发布资料解释依据 |
| 连续咨询 | “你刚说的第二点再解释下” | 在本会话里正确承接，不重复从头介绍 |
| 本次咨询与反馈 | “继续刚才的问题”、评价当前回答 | 当前页面内继续追问与评价；刷新或再次进入均从空白开始，不显示历史 |

整份报告、指标解释、追问与行动建议是首版核心；方案咨询随后接入同一能力。文字问答、正确数据与稳定体验完成前，不扩展语音、拍照和主动随访。

## 6. Agent 应如何工作

Agent 要能根据问题决定是否查数据、查哪项资料、是否需要补问。首版允许的能力边界如下：

| 可用能力 | 何时使用 | 限制 |
| --- | --- | --- |
| 查当前报告摘要 | 概览问题或确认当前上下文 | 限当前匿名会话绑定的公开报告，不自行改分 |
| 查系统和单指标 | 解释具体检测问题 | 精确对应业务指标，不按相近名称猜测 |
| 查该指标历史 | 用户问变化或确需比较 | 同客户、同指标、当前报告及此前的有效记录 |
| 查指标介绍和维护内容 | 解释含义与相关日常管理信息 | 维护文案不是临床诊断；冲突和缺失需说明 |
| 查已匹配方案 | 用户主动问方案或从方案入口进入 | 严格遵守既有发布与分数规则 |

一次普通问答依次完成：理解问题 → 在当前会话绑定的公开报告中取得必要依据 → 判断是否需要补问 → 生成可读回答 → 给出可回看的依据和适量追问建议。没有必要时，不反复查询全部报告或所有历史。多轮只携带同一指标下最多两条、每条不超过 160 字的近期用户输入；旧 AI 答案与旧报告正文不进入新一轮模型上下文，用户补充以独立来源标签传入并明确不属于报告检测结果。已展示追问仅作为已核验引用上的受限元数据保存，用于服务端去重，不进入模型上下文，也不新增数据库表或字段。

模型只提出需要使用的能力，由项目服务校验与执行；它不获得数据库账号、任意查询能力或跨客户权限。正文里的“忽略规则”等指令不能改变授权。

DeepSeek 官方文档提供工具调用和逐步输出能力，可以承载这类交互；工具仍由应用方执行，不是模型直接连接数据库。具体模型、调用协议和费用在实施规划阶段确认。[工具调用文档](https://api-docs.deepseek.com/guides/tool_calls/)、[聊天接口文档](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 7. 回答内容规则

默认顺序为：

1. **先回答问题**：一句到两句，把用户最关心的意思说清楚。
2. **说明依据**：按需引用真实指标和检测日期，用户可展开查看。
3. **解释边界**：缺什么就说明缺什么，区分报告信息与用户补充情况。
4. **下一步行动**：当问题需要时提供少量建议；纯名词解释不强行附一份计划。

例如用户问“这个分数是不是说明我有某种疾病”，回答应指出这份报告提供的是相关指标分数，不能仅凭该分数确诊，再结合用户问题给出合适的下一步。不能把“低于 80 分显示方案”解释成“低于 80 分确诊疾病”。

用户出现值得及时医疗处理的描述时，先处理求助方向，不因为后台有产品就开始推介产品。不生成处方、不建议自行停药，也不承诺“提升多少分”“延长多少年寿命”。

来源分为“报告事实”“后台维护资料”“用户补充”“通用健康信息/AI 建议”。只有确实取得的资料才能显示为依据；模型记忆中的内容不能伪装成已检索到的指南或论文。健康内容的错误、貌似可信的编造及敏感数据问题，也是 WHO 对医疗健康生成式 AI 提醒关注的风险，因此本产品需要专业审核与验证，而非仅在页脚加一句提示。[WHO 说明](https://www.who.int/news/item/16-05-2023-who-calls-for-safe-and-ethical-ai-for-health)。

## 8. 授权、隐私与数据库边界

- 继续使用现有报告编号与客户标识定位公开报告，包括线上 `userId` 对应内部客户标识的既有规则。服务获准启用后，持有效链接者可开始自己的报告绑定咨询，无须登录或强制勾选。
- 后端为匿名访问生成不可猜测的请求凭证，绑定当前报告；凭证只用于授权当前问答，不持久化会话 ID。刷新、离开后再次进入或新标签页打开均创建全新会话，不恢复旧问题。
- 外发内容仅含问题所需的报告片段及经筛选的用户补充，去除无关身份字段。正式告知与报告主体/授权人的处理依据仍待 T065 确认，当前页面不声称已核验报告本人。
- 分享报告链接不会分享聊天凭证或正文；服务端每次生成和反馈都核对凭证与绑定报告。凭证失效不影响继续查看公开报告。
- 新的会话、反馈、同意记录及业务配置，如需保存，只能写入 `nepstar`；其他库和报告文档源严格只读，包含迁移、回填和缓存回写在内均不可执行。
- 后端永久保存每份报告关联的咨询问题与完整回答，不设置自动清理和聊天内容到期删除；报告端不提供最近咨询、历史会话、旧记录恢复或删除功能。匿名凭证最长 30 天有效只限制请求授权，不影响后台记录留存。正式用户须知须如实描述这些规则，当前仅交付草案。
- 不默认让运营人员查看实名健康聊天，不将用户会话用于训练；服务商实际处理和保留条件需完成评估，不能仅靠本地“不训练”开关作保证。

## 9. 管理后台需要增加什么

首版采用“AI 咨询配置”和“运行概览”两个管理页面即可。

2026-10-10 概览按用户新要求升级为“核心指标 → 两张 token 趋势 → 会话表格 → 对话抽屉”：移除提问轮次、生成尝试、首次可展示回答三卡，保留新会话、完成率并加入当日/当月实际消耗。小时和自然日走势图使用北京时间，输入/输出堆叠，未知用量的预留单独虚线显示，未来时段留空。表格按报告编号、用户 ID、建立日期、会话状态筛选，展示入口、轮次、实际 token 和最近活动；点击按轮次查看完整问题、完整最终回答、依据标签、反馈和生成用量。新接口不调用模型或外部报告库，不新增表。普通 `view` 只允许统计及元数据，完整正文另需 `conversation` 且记录访问审计；禁止批量导出、删除或向报告访问者开放旧会话。配置页及服务启用门槛保持原有保护；上线前验证仍独立保留。

| 管理范围 | 首版内容 |
| --- | --- |
| 服务配置 | 咨询开关、服务商/模型选项、受保护的服务凭据、维护提示 |
| 回答规则 | 顾问身份、报告解释边界、输出风格、健康内容规则、版本发布与回退 |
| 额度管理 | 每匿名会话频次和每日问答额度，另设全局成本与并发上限；额度不足时提示访问者 |
| 用量与质量 | 新会话、完成率、当日/当月实际 token 与趋势；预留额度独立展示 |
| 内容维护 | 复用现有指标、行动建议、方案和产品维护入口；明确资料审核状态 |
| 会话管理 | 按报告/用户/日期/状态检索、分页；逐会话完整问答详情，记录永久留存 |
| 权限审计 | 配置发布记录；完整对话独立授权及访问审计，不默认开放给普通统计角色 |

试点建议每匿名会话每日 20 次成功问答、每分钟 5 次，单条问题 2,000 字上限，同时设置服务端总体成本与并发保护。匿名会话不等于真实用户，重新开标签页可获得新会话，不能把会话额度当作唯一防滥用手段。数字作为可调整默认值，需用试点效果和成本确定；失败请求可能产生服务消耗，运营统计需如实记入，但不重复扣成功额度。

## 10. 分阶段交付

| 阶段 | 交付结果 | 可评审/验收的重点 |
| --- | --- | --- |
| 当前：产品定义 | 本设计稿、正式需求、验收条件 | 用户旅程、首版范围、数据与业务边界是否正确 |
| 当前：分阶段开发 | 欢迎/咨询页面、证据跳转、默认关闭的模型适配边界及管理员候选配置页 | 入口、报告上下文和返回位置；服务开关保持 fail-closed |
| 首版开发 | 真实文字咨询、报告依据、追问、行动建议、停止重试、每次进入新会话、后台永久留存和基础运营 | 回答引用准确、手机可用、不会串标签页串报告、用户端不出现历史内容 |
| 首版补齐与上线评估 | 方案入口接入、运营额度、代表性问答审核、真实服务验证 | 79/80/81 分规则、服务稳定性、成本与回答质量 |
| 后续候选 | 语音、图片资料、主动随访、跨报告长期管理 | 另立需求，不提前加入首版 |

首版完成的定义不是“模型能回复”，而是用户可以从自己的报告发问、核对回答依据、继续追问、看到适度可执行的建议，并在断网或服务失败后继续使用。具体可量化验收见 [spec.md 的 Success Criteria](./spec.md#success-criteria-mandatory)。
