## User Scenarios & Testing *(mandatory)*

> 语境：本后台为 NEPSTAR 健康管理后台。当前已有 数据看板/设备管理/数据管理(检测报告/客户)/系统管理 等模块。本特性在后台中新增"健康管理"模块，包含 指标管理、商品管理、方案管理 三个子功能，作为后台可维护的统一目录数据。

### User Story 1 - 维护两级健康指标（指标管理）(Priority: P1)

指标管理员进入"健康管理 → 指标管理"，维护两级健康指标树：先添加一级指标（分类，例如"体重管理"），再在一级指标下面添加二级指标（具体指标项，例如"体脂率"）。**每个指标必须填写唯一的"指标编码"**，便于后续方案引用与其他系统对接。管理员可对两级指标做编辑（改名/改说明/调序）、启用与停用；带有二级子项的一级指标不可直接删除；已被健康方案引用（无论以一级还是二级粒度）的指标不可删除。

**Why this priority**: 指标是 商品、方案 的关联基础与引用对象，应先就绪；本故事自包含、可独立交付验证（不依赖另两个子模块）。

**Independent Test**: 登录后台进入指标管理页，完成 新建一级指标 → 其下新建二级指标（含编码唯一性校验）→ 编辑 → 停用/启用 → 删除保护 的全流程验证，无需其它模块参与。

**Acceptance Scenarios**:

1. **Given** 指标管理员已进入"健康管理 → 指标管理"，**When** 新建一级指标并填写编码 `HT001`、名称"体重管理"，**Then** 保存成功，列表中以一级节点显示，名称与编码正确。
2. **Given** 编码 `HT001` 已存在，**When** 在任一一级指标下再次新建二级指标并提交编码 `HT001`，**Then** 系统拒绝保存并明确提示"指标编码已存在"。
3. **Given** 一级指标"体重管理"下已存在二级指标，**When** 尝试删除该一级指标，**Then** 删除被拒绝，并提示需先处理其下的二级指标。
4. **Given** 二级指标"体脂率"已被某个健康方案引用，**When** 尝试删除"体脂率"，**Then** 删除被拒绝，并提示该指标正被方案引用。
5. **Given** 一级指标可含多个二级指标，**When** 在编辑中调整它们的排序，**Then** 保存后列表按新顺序展示。

### User Story 2 - 配置商品并上传图片（商品管理）(Priority: P1)

商品管理员进入"健康管理 → 商品管理"，新增并维护商品目录。每个商品包含：商品名称、文字说明、**图文详情**、**封面图 + 多张展示图**（图片上传至公司云端存储，存储空间名固定为 `nepstar`）。管理员可在表单中上传、预览、排序、移除图片；列表页以封面缩略图展示并可进入详情。图片只接受图片文件，对数量与大小设限，失败/非法上传给出清晰错误且不产生残缺商品。商品可启用/停用；被任一健康方案引用的商品不可删除。

**Why this priority**: 商品是独立、完整的目录数据，可直接上线供方案引用；与指标无关，可独立交付。

**Independent Test**: 登录后台进入商品管理页，验证 新建商品（含多图上传 OSS、封面、图文详情）→ 编辑图片集合与详情 → 列表缩略图/详情展示 → 删除保护 全流程，无需指标/方案模块参与。

**Acceptance Scenarios**:

1. **Given** 商品管理员处于新建商品表单，**When** 填写名称、上传 1 张图片作为封面并保存，**Then** 商品创建成功，列表中显示封面缩略图与名称。
2. **Given** 商品支持多张展示图，**When** 管理员一次上传多张图片并调整顺序，**Then** 保存后详情中按新顺序显示全部图片，第一张作为封面。
3. **Given** 管理员尝试上传一个非图片文件（如 `.exe`）或超过大小上限的文件，**When** 上传，**Then** 上传被拒绝并提示文件类型/大小不符。
4. **Given** 管理员未上传任何图片便尝试保存商品，**Then** 系统提示至少需要一张图片，禁止保存不完整商品。
5. **Given** 某商品已被某个健康方案引用，**When** 尝试删除该商品，**Then** 删除被拒绝并提示被方案引用。

---

### User Story 3 - 配置健康方案并关联商品与指标（方案管理）(Priority: P2)

方案管理员进入"健康管理 → 方案管理"，创建和维护健康方案。每个方案包含名称、描述/目标、启用状态。方案可**关联多个商品**（用于推荐售卖/搭配）；方案可**关联一组健康指标**，关联粒度既可是一级指标也可是二级指标。**采用"严格精确"关联规则：勾选一个一级指标，不自动包含其下的二级指标，方案实际关联的就是勾选的节点本身**。方案详情集中展示所关联的商品列表与指标列表。管理员可在编辑时增删、排序关联项；重复勾选会被合并去重。方案自身的删除不受引用限制，但需二次确认。

**Why this priority**: 方案同时依赖 商品 与 指标 两类目录，置于最后；其价值最高但独立可测（只读地使用已就绪的数据）。

**Independent Test**: 待指标与商品已存在（可用本特性内种子/手工录入的最小集），登录进入方案管理页，验证 新建方案 → 勾选多个商品 → 以一级/二级粒度勾选指标 → 详情展示一致 → 编辑重选 → 删除方案 全流程。

**Acceptance Scenarios**:

1. **Given** 目录中已有商品与两级指标，**When** 新建方案，勾选 2 个商品，并按一级粒度勾选"体重管理"、按二级粒度勾选"体脂率"，保存，**Then** 方案创建成功。
2. **Given** 上述已保存方案，**When** 查看方案详情，**Then** 方案集中展示所关联的 2 个商品与指标（"体重管理"以一级展示，"体脂率"归入其所属一级下以二级展示），且与保存时勾选一致、无遗漏无重复。
3. **Given** 方案按一级粒度勾选了"体重管理"，**Then** 该方案**不**自动包含"体重管理"下未勾选的二级指标——严格精确关联（与勾选的一级节点同级的其下子项不在关联内）。
4. **Given** 管理员在编辑方案时对同一指标重复勾选，**When** 保存，**Then** 关联被去重，不产生重复记录。
5. **Given** 方案已停用，**When** 停用后再次查看/编辑，**Then** 其已保存的商品与指标关联完整保留、不受停用影响。

### Edge Cases

- **图片上传边界**：非图片文件、超大文件、数量超上限 → 上传被拒绝并给出明确错误；上传失败不残留半成品商品。
- **保存不完整数据**：未完成图片上传/未上传封面即保存商品 → 阻止保存并提示必填项。
- **编码冲突**：指标编码在任何层级重复 → 拒绝并提示唯一性；跨一级/二级也不可重复。
- **删除保护**：①含二级子项的一级指标 ②被方案引用的指标（一级或二级粒度）③被方案引用的商品 → 均禁止删除，给出可理解提示。
- **状态与引用并存**：被方案引用的指标/商品被停用 → 停用允许；方案详情中对已停用关联项给出"已停用"标记，方案仍可正常查看与编辑。
- **重复关联去重**：同一方案内同一商品/指标只允许出现一次，重复勾选自动合并。
- **空关联**：方案允许不关联任何商品或指标（最小可保存的空方案），列表与详情按空状态友好展示。
- **目录为空时**：指标/商品尚未建立任何数据时，方案中的选择器应给出"暂无数据"提示而非报错。
- **并发覆盖**：两个管理员同时编辑同一方案/商品/指标并保存 → 后者覆盖前者（沿用现有后台约定的最后写入胜出），不得产生数据错乱或重复行。

## Requirements *(mandatory)*

### Functional Requirements

**模块级（导航与权限）**

- **FR-001**: 系统必须在后台导航中提供新的顶级入口「健康管理」，其下包含「指标管理」「商品管理」「方案管理」三个子页面；仅已登录且被授权（现有 账号-角色-菜单 权限体系）的账号可见可用。
- **FR-002**: 三个子页面均提供完整的列表（分页）、检索、新建、编辑、删除、启用/停用操作；每次操作后即时反馈成功或失败原因。
- **FR-003**: 指标/商品/方案 的名称与说明字段，v1 均只维护单一语言（中文）内容；多语言（英/西）名称与描述不在 v1 范围内。
- **FR-004**: v1 明确**不**包含商品的价格、库存、规格参数、独立商品分类等电商字段，以及"基于检测报告异常指标自动推荐方案"等消费端联动功能。

**指标管理**

- **FR-101**: 系统必须允许管理员创建一级指标，字段至少包括：指标名称（必填）、指标编码（必填）、说明（可选）、排序、状态（启用/停用）。
- **FR-102**: 系统必须允许管理员在某个一级指标下创建二级指标，字段至少包括：所属一级指标、指标名称（必填）、指标编码（必填）、说明（可选）、排序、状态（启用/停用）。
- **FR-103**: 指标编码为必填且在整个指标库内唯一（跨一级/二级均不可重复）；重复提交必须被拒绝并给出明确提示。
- **FR-104**: 一级与二级指标均支持编辑其名称、编码、说明、排序与状态；状态可在启用/停用间切换。
- **FR-105**: 指标列表必须以两级树形结构展示（一级节点可折叠/展开其二级子项），并支持按名称或编码检索定位。
- **FR-106**: 系统必须实施删除保护：含二级子项的一级指标不可删除；已被任一方案引用（一级或二级粒度）的指标不可删除；删除被拒绝时给出可理解的原因提示。

**商品管理**

- **FR-201**: 系统必须允许管理员创建与编辑商品，字段至少包括：商品名称（必填）、文字说明、图文详情、封面图、多张展示图、排序、状态（启用/停用）。
- **FR-202**: 系统必须将商品图片上传至公司指定的云端存储空间（bucket 固定为 `nepstar`）；每个商品可上传多张图片，第一张作为封面图。
- **FR-203**: 系统必须在表单中支持对已上传图片的预览、排序与移除；保存后以当前图片集合为准（含封面）。
- **FR-204**: 系统必须仅接受图片类型文件，并对单张大小与单商品图片数量设限；对类型不符、超限或上传失败给出清晰错误，且不得产生不完整/无图商品。
- **FR-205**: 商品列表必须展示封面缩略图与名称；商品详情/编辑视图必须展示图文详情与全部展示图。
- **FR-206**: 系统必须禁止删除被任一方案引用的商品，并给出可理解的提示。

**方案管理**

- **FR-301**: 系统必须允许管理员创建与编辑健康方案，字段至少包括：方案名称（必填）、描述/目标、排序、状态（启用/停用）。
- **FR-302**: 系统必须允许方案关联一个或多个商品，并按添加顺序在方案中展示；编辑时可增删、排序所关联商品。
- **FR-303**: 系统必须允许方案关联一个或多个指标，关联粒度可为一二级指标中的任一级别；采用**严格精确关联**：勾选一级指标不自动包含其下二级子项，方案实际关联的即所勾选的节点。
- **FR-304**: 系统必须对方案内关联项去重：同一方案内不得出现重复的商品关联或重复的指标关联。
- **FR-305**: 系统必须在方案详情中集中展示所关联的商品列表与指标列表（指标按所属一级分组展示并标明其关联粒度）。
- **FR-306**: 方案的启用/停用不影响其已保存的关联内容；方案自身可删除，删除前需二次确认，删除不受外部引用限制。

### Key Entities *(include if feature involves data)*

- **一级指标（健康指标分类）**: 健康指标的最高分组。关键属性：指标编码（唯一）、名称、说明、排序、状态；作为二级指标的上级，可被方案按"一级粒度"直接引用。
- **二级指标（健康指标项）**: 归属于某一级指标的具体指标项。关键属性：所属一级指标、指标编码（全局唯一）、名称、说明、排序、状态；可被方案按"二级粒度"直接引用。
- **商品**: 后台维护、可上传到云端存储并对外展示的健康商品。关键属性：名称、封面图、多张展示图、图文详情、文字说明、排序、状态；可被多个方案引用。
- **健康方案**: 关联了推荐商品与关注指标的健康改善方案。关键属性：名称、描述/目标、状态、排序；与商品为多对多关系，与指标为多对多关系。
- **方案-商品 关联**: 记录某方案引用某商品（含顺序）；引用关系而非拷贝，商品信息变更时方案处随之同步显示。
- **方案-指标 关联**: 记录某方案以何种粒度（一级/二级）引用了哪个指标；引用关系而非拷贝，指标信息变更时方案处随之同步显示。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 授权管理员可在每个子页面 1 分钟内完成"新建 → 保存 → 列表可见"的完整闭环（在验收环境含数据量级的目录数据下）。
- **SC-002**: 指标编码唯一性约束 100% 生效——任何层级、任何时刻的重复编码提交均被拒绝。
- **SC-003**: 保存成功的每个商品至少包含 1 张可在列表与详情中正常显示的图片；验收用例中商品图片无法显示的比例为 0。
- **SC-004**: 方案保存后，其详情中展示的商品与指标关联与保存时勾选完全一致：无遗漏、无重复、顺序正确。
- **SC-005**: 一级/二级指标树在不大于 1,000 条指标的目录数据量下，可于 1 秒内完成首次加载与按名称/编码检索。
- **SC-006**: 三类删除保护（含子级的一级指标、被方案引用的指标、被方案引用的商品）在全部验收用例中均生效且提示清晰，失败率 0%。
- **SC-007**: 5 个授权用户在验收环境同时对三个子页执行增删改查与图片上传，无数据互相覆盖、重复行或异常错误。

## Assumptions

- **目录范围（据用户确认）**：商品/方案/指标为**全公司统一目录**，不做按组织(org)的归属与过滤；由具备权限的后台账号统一维护（与现有 角色/菜单 等全局配置一致）。
- **图片存储**：使用公司既定/指定的阿里云 OSS，bucket 名称固定为 `nepstar`；上传成功后保存长期有效的图片地址，用于列表与详情展示。OSS 访问凭据由后台安全保管、不落入前台页面与代码库。
- **图片规格（据用户确认）**：每个商品含 1 张封面图 + 多张展示图 + 图文详情；图片数量上限、单张大小上限等参数由实施阶段确定，验收按当时设定的阈值执行。
- **关联语义（据用户确认）**：方案-指标采用**严格精确关联**——勾选一级指标不自动包含其下二级子项；方案展示/统计以"直接勾选的节点"为准。
- **引用而非拷贝**：方案与商品/指标之间为引用关系；被引用对象的删除被阻止（v1 不做级联删除、不做"替换提示"的替代方案）。
- **指标编码**：由管理员填写并全局唯一；本模块仅做唯一性校验，不承担与外部/遗留检测系统指标编码的映射（如有，另行迭代）。
- **消费方范围**：v1 仅在后台维护与展示，暂不面向顾客端/检测报告展示页输出这些数据；后续接入作为独立迭代。
- **内容语言（据澄清确认）**：v1 指标/商品/方案的名称与说明仅存中文单一语言；后台 UI 文案仍为现有中/英/西三语体系，但目录数据内容不做多语录入。后续如需面向多语客户展示，再扩展多语字段（届时需数据补录/迁移）。
- **商品字段范围（据澄清确认）**：v1 商品不含 价格/库存/规格/独立商品分类 等电商字段；若业务需要可作为后续迭代独立增加。
- **权限模型**：沿用现有 账号-角色-菜单 体系；v1 至少保证 `admin` 账号可完整使用全部新功能，其它角色按需授权（含新增的页面）。
- **数据量**：目录类数据（指标、商品、方案）体量小，无特殊性能/分页规模要求。
- **数据敏感度**：本模块仅涉及商品目录与健康方案配置，不含客户个人身份信息(PII)；现有 PII 掩码逻辑不受影响。
