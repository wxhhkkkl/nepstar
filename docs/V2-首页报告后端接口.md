# V2 首页报告后端接口设计

> 适用范围：`reportFront/report-v2`  
> 文档状态：接口设计建议，尚未实现  
> 数据阶段：先支持现有模拟数据，后续替换为真实检测数据

## 1. 目标

为 V2 长寿指数报告首页和系统二级详情页提供稳定的数据接口，支持以下现有页面能力：

- 报告基础信息与总分展示；
- 总分低于 70 分时的警示色和光晕效果；
- 实际年龄、生理年龄、健康预期寿命等摘要指标；
- 按规则展示适用的身体系统；
- 低分且有产品推荐的系统优先排序；
- 首页系统卡片、图表和指标摘要；
- 系统二级详情页的评分构成、直接采集、结论和行动建议；
- 内分泌和骨骼等问题对应的健康管理方案及商品；
- AI 长寿咨询入口配置；
- 后续扩展报告长图下载。

## 2. 当前后端能力与缺口

### 2.1 已有接口

当前后台已有以下管理端接口：

- `GET /api/v1/reports`
- `GET /api/v1/reports/{report_id}`
- `/api/v1/indicators` 指标配置接口
- `/api/v1/plans` 健康方案配置接口
- `/api/v1/products` 商品配置接口

其中 `GET /api/v1/reports/{report_id}` 当前只返回报告基础信息，并固定返回空的 `items`：

```json
{
  "report": {
    "report_id": 1,
    "report_code": "LS-20260803-0286",
    "customer_id": 1001,
    "inspect_date": "2026-08-03T10:00:00",
    "total_score": 68
  },
  "items": []
}
```

### 2.2 现有接口不能直接支撑 V2 的原因

- 报告接口没有系统得分和二级指标结果；
- 没有首页图表需要的序列数据；
- 没有年龄和健康预期寿命等报告摘要；
- 没有把报告中的异常指标与健康方案、商品进行组合；
- 指标、方案和商品接口属于后台配置接口，不是面向报告用户的展示接口；
- 后台报告接口需要管理端权限，不适合直接暴露给报告查看页面。

因此应保留现有后台管理接口，并新增一组面向报告展示的聚合接口。

## 3. 建议接口清单

第一阶段最少需要两个接口：

| 接口 | 用途 | 优先级 |
| --- | --- | --- |
| `GET /api/v1/report-view/{reportCode}/home` | 获取首页全部展示数据 | P0 |
| `GET /api/v1/report-view/{reportCode}/systems/{systemCode}` | 获取系统二级详情数据 | P0 |

后续可增加：

| 接口 | 用途 | 优先级 |
| --- | --- | --- |
| `GET /api/v1/report-view/{reportCode}/download` | 获取或生成报告长图/PDF | P2 |
| `POST /api/v1/report-view/{reportCode}/ai-session` | 创建与报告上下文关联的 AI 咨询会话 | P2 |

当前“保存报告”按钮已隐藏，第一阶段不需要实现下载接口。AI 咨询当前是静态入口，第一阶段只需要在首页接口中返回入口配置。

### 5.3 关键要求

- 二级详情页必须使用与首页同一份报告结果，不能重新使用另一套固定分数；
- 首页系统得分、详情系统得分和指标得分必须完全一致；
- 首页存在产品推荐时，进入对应系统详情页也必须返回同一方案和商品；
- 推荐内容应紧跟对应问题展示；
- 直接采集值不参与加权评分时，应通过字段明确说明。

## 6. 推荐方案匹配规则

后台目前已经建立以下配置关系：

- `松果体分泌（SYS_ENDOCRINE_PINEAL）` → `松果体睡眠健康管理方案` → `睡眠健康管理礼盒`
- `骨质疏松（SYS_BONE_OSTEOPOROSIS）` → `骨质疏松钙流失健康管理方案` → `钙流失健康管理礼盒`

建议后端按以下关联链查询：

```text
报告二级指标结果
  → sa_indicator
  → sa_plan_indicator
  → sa_plan
  → sa_plan_product
  → sa_product
```

匹配规则：

1. 使用二级指标编码匹配方案，不使用一级系统名称模糊匹配；
2. 只有启用状态的指标、方案和商品可以出现在报告中；
3. 指标达到方案配置的触发条件后才返回推荐；
4. 同一指标命中多个方案时，按方案优先级和排序字段选择；
5. 同一方案可以返回一个或多个商品，商品按配置顺序展示；
6. 首页和详情页调用同一个推荐组装服务，避免出现推荐不一致。

当前管理表只有关联关系。如果要支持真正的自动推荐，建议为 `sa_plan_indicator` 增加以下配置：

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| `operator` | `lt` | 比较方式，例如小于、区间内 |
| `threshold_min` | `null` | 最小阈值 |
| `threshold_max` | `60` | 最大阈值 |
| `priority` | `100` | 多方案命中时的优先级 |
| `enabled` | `1` | 是否启用 |

## 7. 系统排序规则

后端建议直接返回最终 `sortOrder`，前端按该字段渲染，不再自行推断业务顺序。

推荐排序规则：

1. 低分且命中产品推荐的系统；
2. 其他低分系统；
3. 正常系统；
4. 优势系统；
5. 不适用于当前用户的系统不返回，或返回 `applicable: false` 由前端隐藏。

同一组内可依次按以下字段排序：

1. 方案优先级降序；
2. 系统得分升序；
3. 后台配置顺序升序。

V2 当前期望内分泌和骨骼靠前展示，因为两者得分低且存在产品推荐。

## 8. 总分与警示状态规则

建议由后端返回原始得分和阈值，由前端统一负责视觉效果：

```text
totalScore < warningThreshold  → 警示状态
totalScore >= warningThreshold → 正常状态
```

以下视觉属性继续由前端维护，不建议存入报告业务数据：

- 分数颜色；
- 光晕颜色；
- 分割线颜色；
- 卡片 CSS 色调；
- 图标和布局样式。

后端只需保证 `totalScore` 和 `warningThreshold` 正确。V2 当前为 `68 < 70`，页面应呈现警示色、警示光晕和对应分割线颜色。

## 9. 数据来源与建议表结构

### 9.1 已有配置数据

后台已有健康管理配置表，可继续使用：

- `sa_indicator`：一级、二级指标定义；
- `sa_product`：商品定义；
- `sa_plan`：健康管理方案；
- `sa_plan_indicator`：方案与指标关联；
- `sa_plan_product`：方案与商品关联。

### 9.2 仍需补齐的报告结果数据

现有本地数据库缺少旧系统真实报告结果表。要支撑首页，需要从旧库接入或新增以下逻辑数据：

#### 报告主表

- 报告编号；
- 客户 ID；
- 检测日期；
- 用户性别；
- 总分；
- 实际年龄；
- 生理年龄；
- 健康预期寿命；
- 同龄人对比百分比；
- 总体结论。

#### 报告系统结果表

- 报告 ID；
- 一级系统指标 ID；
- 系统得分；
- 状态；
- 摘要；
- 解释；
- 展示顺序。

#### 报告二级指标结果表

- 报告 ID；
- 二级指标 ID；
- 指标得分；
- 权重；
- 原始值；
- 单位；
- 是否参与加权；
- 异常级别。

#### 报告图表数据

图表数据可从二级指标结果动态组装。只有心血管“近 6 次趋势”这类跨报告图表需要额外查询历史报告结果。

## 10. 前端字段映射

当前 V2 模拟数据位于：

`reportFront/report-v2/src/data/report.js`

接入接口后建议保持页面组件所需的前端 ViewModel 结构不变，在单独的数据适配层完成接口字段转换。这样可以减少 UI 组件改动。

当前需要逐步移除的硬编码包括：

- 报告总分 68；
- “内分泌与骨骼”重点说明；
- 首页重点分值 54；
- 肺功能血氧饱和度 98%；
- 各系统卡片的固定说明文案；
- 系统和二级指标得分；
- 图表序列；
- 推荐方案和商品信息。

建议保留在前端的内容包括：

- CSS 类名和主题色映射；
- SVG 图标；
- 页面布局；
- 路由名称；
- 分数到视觉状态的映射逻辑。

## 11. 鉴权与访问安全

后台管理接口继续使用管理员 JWT。报告展示接口不要直接复用管理员权限。

第一阶段为了兼容现有报告链接，可以使用：

```text
reportCode + customerId
```

但正式环境不建议仅依赖这两个可猜测参数。建议报告链接增加短时或可撤销的签名令牌：

```http
GET /api/v1/report-view/{reportCode}/home?token={signedToken}
```

服务端需要校验令牌与报告、客户的绑定关系，避免用户遍历查看其他人的健康报告。

## 12. 错误响应建议

| HTTP 状态 | message | 场景 |
| --- | --- | --- |
| 400 | `report.invalid_request` | 参数格式错误 |
| 401 | `report.invalid_token` | 报告访问令牌无效 |
| 403 | `report.access_denied` | 报告与客户不匹配 |
| 404 | `report.not_found` | 报告不存在 |
| 404 | `report.system_not_found` | 系统不属于该报告 |
| 409 | `report.not_ready` | 报告尚未计算完成 |
| 500 | `report.assemble_failed` | 报告聚合失败 |

## 13. 实施顺序

### P0：完成页面真实数据闭环

1. 确定真实报告结果表或旧库字段；
2. 实现报告首页聚合服务；
3. 实现系统详情聚合服务；
4. 接入指标、方案、商品关联；
5. 保证首页与详情页使用同一得分和推荐结果；
6. V2 前端新增 API 层和数据适配层；
7. 保留模拟数据作为接口异常时的开发环境回退数据。

### P1：后台可配置化

1. 增加方案触发阈值和优先级；
2. 增加系统展示顺序配置；
3. 完善商品正式图片地址；
4. 将结论和行动建议改为模板或规则配置。

### P2：扩展能力

1. 报告长图/PDF 生成；
2. AI 咨询真实会话接口；
3. 历史趋势查询；
4. 访问日志和报告分享控制。

## 14. 第一阶段验收标准

- V2 首页不依赖 `report.js` 中的业务模拟值即可完整显示；
- 总分为 68 且阈值为 70 时，页面正确进入警示状态；
- 内分泌得分为 58，松果体分泌得分为 48；
- 骨骼得分为 54，骨质疏松得分为 48；
- 内分泌和骨骼在首页靠前展示；
- 内分泌下展示睡眠健康管理方案和对应商品；
- 骨骼下展示钙流失健康管理方案和对应商品；
- 从首页进入二级详情页后，系统得分、指标得分和推荐内容完全一致；
- 女性报告隐藏男性功能，男性报告隐藏女性功能；
- 商品图片完整展示，接口返回可访问的正式图片 URL；
- 接口异常、报告不存在和报告未生成时，页面有明确错误状态。

## 15. 结论

V2 首页不应分别调用报告、指标、方案和商品等多个后台管理接口后由前端自行拼装。正确做法是由后端新增报告展示聚合服务，一次性返回已经完成权限校验、系统排序、指标匹配和推荐组装的数据。

第一阶段实现“首页聚合接口 + 系统详情接口”即可覆盖当前 V2 的核心页面。下载报告和 AI 会话可在主数据链路稳定后再接入。
